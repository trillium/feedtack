# Fable Imaginings — Where Feedtack Wants to Go

> Speculative design doc, 2026-07-06. Written after a full pass over the codebase,
> `DESIGN_QUESTIONS.md`, `SPEC.md`, and the openspec history. Opinions included, as requested.

## The real product

Feedtack is the mechanism by which people who can see problems but can't fix them hand work to systems that can fix them but can't see them. A copywriter knows the hero heading is wrong; a partner knows the button feels broken; neither can act on that knowledge, so today it decays into a Slack message that a developer must reverse-engineer back into coordinates, components, and intent. Feedtack inverts that: the stakeholder points at the thing, and the payload carries enough machine-readable context — selector, component name, ancestor chain, content hash, viewport — that a machine can find the code before a human ever reads the complaint. It is not a feedback widget. It is a work-routing protocol whose atomic unit is "a pointed-at element plus intent," and the answer to DESIGN_QUESTIONS.md question 1 has been sitting there since it was written: the target reader of a tack is an LLM, and the developer is the escalation path.

## Five underused capabilities

**1. Component names are a code-location oracle being treated as garnish.** The fiber walker (`src/capture/fiber.ts`) plus the ancestor chain (`src/capture/target.ts`) put React component names into every payload — and then nothing consumes them. `componentName: "PricingCard"` is a grep away from the source file in almost any repo. The payload already speaks the developer's vocabulary; no downstream tool has been taught to listen. A twenty-line script that maps `componentName` → file path would convert every tack into a jump-to-definition.

**2. Field-path selectors are a headless CMS schema declared in-place.** `data-feedtack-field="coaching.hero.heading"` (openspec v0-4-0, D3) gives every piece of content a stable, dot-path address that survives redesigns, refactors, and DOM churn — exactly the property CSS selectors lack. Feedtack accidentally built CMS addressing without building a CMS. Those paths are LLM-addressable identifiers: an agent told "fix `coaching.hero.heading`" needs no DOM understanding at all, just `saveField()`.

**3. Content hashes could auto-expire stale feedback, and don't.** The approval system hashes content to detect drift (`useContentApproval`, SHA-256 truncated to 12 hex chars), but tack payloads capture element text too (`src/capture/content.ts`) and nobody ever checks it again. A tack whose target's content hash no longer matches is probably about something that already changed — that is free first-pass triage ("this feedback may be stale; the element was edited after it was filed") using machinery that already exists on both sides.

**4. `checkDeploy()` is a general attestation ledger wearing a content-approval costume.** What it actually implements (`useContentApproval.ts`) is "a named human approved state X at hash Y, and here is the delta since." That primitive gates anything: visual regression sign-off, legal review of terms pages, translation freshness. It is framed as a niche content feature and exported from one hook; it deserves to be the headline of the adapter contract.

**5. The Playwright reporter is a review surface for non-developers, shipped and unmarketed.** `examples/tack-server/playwright-reporter.ts` patches the HTML report so anyone can drop pins on test results — meaning a designer can annotate a visual-regression run without a GitHub account, and the tack lands in `.feedtack/` at the git root where any coding agent can read it. That is "PR review comments for people who don't use PRs," buried in an examples directory.

## Three new directions

**`feedtack triage` — the CLI that closes the loop.** A command that reads `.feedtack/*.json`, uses `componentName` + selector + field-path to locate the implicated source, asks an LLM for a diagnosis, and writes its findings back into the tack's `replies` array — draft patch attached when it's confident. Every ingredient exists: tacks are already JSON in the repo, payloads already carry code-shaped identifiers, and the thread model already supports replies from any actor. A sprint gets you read-tack → grep-repo → reply-with-diagnosis; the PR-opening flourish can come later. This is the product DESIGN_QUESTIONS.md question 1 describes, and nothing in the repo builds it yet.

**Copy desk — in-place editing that opens a PR.** `useContentEdit` already does hydrate-on-activate, blur-to-save, and session change tracking. Pair it with an adapter whose `saveField()` writes to the source files (a `GitAdapter` cousin of `DiskAdapter`) and you have "your copywriter edits production text in the browser; a branch with the diff appears." The v0-5-0 machinery was built for this and stops one adapter short of it. A sprint: field-path → JSON/MDX source mapping config, `saveField` writes the file, `simple-git` commits to a branch.

**Visual regression court.** Wire the Playwright reporter, the resolution system, and `checkDeploy()` into one flow: every changed screenshot in a visual run becomes a tackable card; the release gate is "all visual-diff tacks resolved." Designers approve by resolving; CI blocks on the pending list. This is composition, not construction — reporter (exists) + resolutions (exist) + deploy gate (exists) + one GitHub Action that calls the tack-server's pending endpoint.

## The LLM-native version

Here is the surprise: the schema is already LLM-native — it is the delivery loop that is still human-shaped. The payload doc-comments literally say `ancestors` exists "for LLM element location"; `best_effort` is a machine-readable confidence bit; question 11's answer asks for "a chat where other team members or an LLM can reply." The data model anticipated agents. What ships today, though, is webhook-to-spreadsheet: a pipeline that terminates in human eyeballs.

The LLM-native version changes the lifecycle, not the schema. A tack lands in `.feedtack/` and is *unclaimed work*, not a notification. An agent with repo access claims it, uses the selector to screenshot and confirm the element (Playwright can navigate to `page.url`, scroll to `scrollY`, and query the selector — the repro recipe is embedded in every payload), uses `componentName` and the ancestor chain to locate source, and replies in-thread as a `FeedtackUser` with `role: 'agent'` — the user model already permits this; it just needs the convention blessed. For content-shaped tacks, the agent's exit criterion is mechanical: edit via `saveField()`, then `rescan()` until the hash matches an approved state. For code-shaped tacks, the reply carries a branch name and the human decides. The stakeholder experience becomes: point at a thing, describe what's wrong, and watch the thread answer you — sometimes in minutes, with a preview link. Three small additions unlock all of it: an agent-actor convention in `FeedtackUser`, a claim/unclaimed field on `FeedbackItem` so two agents don't collide, and a documented reply format for "here is my diagnosis / here is my patch." No schema break; `schemaVersion` 2.x survives.

## What to kill

**Document-percentage pin coordinates (`xPct`/`yPct`).** They encode screenshot-thinking — a pin as a point on a page image — and they are wrong on every responsive breakpoint, which is why `useAnchoredPins` exists to re-derive positions from the element instead. The element anchor (selector + ancestors + rect) is the real address; the percentages are a fallback that mostly produces confidently misplaced pins. Keep raw `x`/`y` for the forensic record, delete the percentage fields at the next schema major, and let anchoring be the only positioning story.

**The sentiment toggle.** Question 6 already admits it is "concept scope, not directly actionable." A good/bad binary next to a freeform comment adds a decision for the stakeholder and no information an LLM triager can't extract better from the comment text itself. It survives because every feedback tool has one. Feedtack's unit of value is a located, described problem — not a mood. Kill it from the capture UI; keep the field nullable in the schema so old payloads parse.

**Site/Page scope tabs in the React modal.** The element tack is the product — it is the thing no other tool does. Site-scoped freeform comments are a worse Slack message with extra steps, and they drag along a modal, tabs, a compose-scope state machine, and rescoping roles (`rescopeRoles`, breakpoint-aware rescoping!) whose complexity is wildly out of proportion to "sometimes feedback isn't about one element." One honest fallback — a pin dropped on `<body>` — covers the general-comment case inside the element model. The modal machinery is the single largest chunk of React-path complexity that the extension and IIFE paths prove unnecessary.

Honorable mention, not killed but frozen: the theming surface (theme tokens + per-component class overrides + custom pin icons). It is finished, tested, and fine — but it is customization depth for an internal-stakeholder tool, and every new UI feature now pays a tax to support it. Freeze it; spend that budget on the triage loop, which is the actual promise of the product.
